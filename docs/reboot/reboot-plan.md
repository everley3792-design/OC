# OC Shimeji 重構（Reboot）開發計畫

> 狀態：**計畫書，等待玩家確認**（第十節列出需要你決定的事）。確認之前不動任何程式碼。
> 預設角色圖：`docs/reboot/cinnamon-roll.png`（3072×3072、透明背景 RGBA，玩家提供的原創角色「肉桂捲」）。

## 〇、前提與原則

### 重構前提（最高優先）
1. **歸零**：舊的程式碼、存檔格式、角色資料**全部不沿用**。
   - 舊版本只留在 git 歷史裡（標籤 `legacy-0.17.3`），新專案不讀舊存檔、不轉換。
2. **定位**：自主生活模擬（觀察系）＋深度桌寵。
   - 玩家匯入自己的原創角色（OC），日常照顧、互動、看牠們自己過日子。
3. **沒有捏臉**：沒有內建的捏臉或紙娃娃系統；角色只來自匯入，或用預設角色。
4. **Android 手機優先**：
   - 觸控操作；
   - 系統懸浮窗；
   - 背景省電；
   - 各種螢幕比例。

### 參考作品怎麼用
只取**設計原則**：節奏、回饋感、系統之間怎麼互相影響。**不使用**任何參考作品的角色、名稱、Logo、介面圖形、地圖、音效、文字或素材。所有美術與聲音都是原創。

| 參考 | 取用的原則 |
|---|---|
| 角色觀察屋 | 放進來就會自己生活；以「看」為主的視角；匯入門檻低 |
| Tomodachi Life | 角色之間無厘頭的自主社交；性格的化學反應；角色帶著煩惱來找玩家 |
| inZOI／The Sims 4 | 需求值；物件「廣告」自己能滿足什麼需求（smart object）；自主 AI；生活節奏 |
| 集合啦！動物森友會 | 現實時間同步；溫暖的小鎮氛圍；佈置住宅；每天都有一點新東西 |
| 任天堂整體 | 圓潤、柔和、高可讀性；每個操作都有回饋（聲音、彈跳、粒子）；很少的文字 |

### 從舊版學到、這次一開始就要做對的事
這些教訓保留（不是保留程式碼）：
- **一個模擬、一個時鐘**：生活只由一個確定性的模擬核心推進；畫面、桌寵、背景都只是它的觀看者。
- **效能預算先定**：舊版平均約 20 fps 的教訓 → 每個場景有繪製次數、記憶體、耗電的上限，自動化測試檢查。
- **桌寵不是第二套大腦**：舊版桌寵只能讀快照，App 關著時角色是「停住」的。新版讓桌寵與遊戲共用同一個模擬核心。
- **可測試**：每個系統都要能在電腦上（JVM）用單元測試和截圖測試驗證；手機上必須驗證的項目一律明列。
- **不做假功能**；未成年角色絕不涉及戀愛；重大改變（在一起、永久特質）要玩家同意。

## 一、遊戲核心循環與設計支柱

### 1.1 設計支柱（每個功能都要回答「它支撐哪一根」）
1. **牠們真的在生活**：不需要玩家，角色也會吃、睡、聊天、吵架、和好；玩家回來時有故事可看。
2. **你的角色，原汁原味**：匯入的圖保持原樣、動作自然；一張圖就能動，畫得越多越生動。
3. **一直都在身邊**：角色可以跳出 App 到手機桌面陪你；桌面上的事會回到小鎮的生活裡。
4. **溫暖、好懂、手感好**：圓潤柔和的畫面，單手就能玩，每一下觸碰都有回應。
5. **輕鬆，不催促**：沒有懲罰性的倒數；需求低落只會讓角色比較沒精神，不會死掉或逃走。

### 1.2 核心循環

**每一次打開（約 1–5 分鐘）**：
1. 「你不在的時候」：一張卡片，有幾件大事與名場面；
2. 看看大家在做什麼：點角色看狀態；
3. 處理一兩件事：有人肚子餓、有人來商量煩惱、兩人吵架了要不要幫忙；
4. 摸摸、餵食、送禮，角色的反應依個性不同；
5. 把一個角色帶到桌面上，關掉 App。

**每天（現實時間）**：
- 一天的節奏：早上起床、上午活動、午餐、下午、晚餐、夜晚、睡覺；
- 每天的小新鮮事：商店換貨、鎮上的小事件、角色的心願；
- 每天結算關係。

**長期（週、月）**：
- 關係慢慢變化：陌生 → 朋友 → 好友 → 知己；成年角色在玩家同意下可以在一起；
- 收集家具，佈置房子；
- 匯入更多 OC，小鎮變熱鬧；
- 回憶與相簿慢慢累積。

**桌寵循環（白天在手機上）**：
1. 角色在桌面上走、坐、睡、爬螢幕邊緣；
2. 玩家點、摸、拎起、丟出去；
3. 需求低時討食、討摸；點一下就能在桌面上餵牠；
4. 這些全部算進小鎮的生活：被摸過心情變好；在桌面上餓了，回到小鎮也是餓的。

### 1.3 資源與動機（只用溫和的）
- **星幣**：照顧角色、完成小請求、出售收成或作品得到；用來買家具、食物、禮物。沒有付費貨幣。
- **回憶**：每個重要時刻一張卡；相簿與時間線。
- **心願**：角色自己提出的小目標（想吃某道菜、想和誰變好）；達成時有反應與回憶。

## 二、技術選型與 Android 桌寵底層架構

### 2.1 選型比較與建議

| 方案 | 小鎮畫面 | 桌寵懸浮窗 | 共用模擬核心 | 在本環境建置 | 自動化測試 | 評估 |
|---|---|---|---|---|---|---|
| **A. 原生 Kotlin（建議）** | 自製輕量 2D 渲染（OpenGL ES 2.0） | 原生小視窗，同一套渲染 | ✅ 同一個 Kotlin 核心 | ✅ 現有的離線管線 | JVM 單元測試＋JVM 截圖渲染 | 效能、耗電、桌寵整合最好 |
| B. WebView（舊版的做法） | HTML/WebGL | 原生另寫一套 | ❌ 兩套（舊版的問題） | ✅ | Chromium 測試最方便 | 已知效能與「桌寵是快照」問題 |
| C. Godot 4 | 引擎 | 無法把引擎畫面放進多個系統懸浮小視窗 | 部分 | ❌ 需下載匯出模板 | 中 | 不適合深度桌寵 |
| D. Unity | 引擎 | 同上，記憶體大 | 部分 | ❌ 無法下載 | 中 | 不適合 |
| E. Jetpack Compose＋原生 | Compose | 原生 | ✅ | ❌ 需要 Google Maven（本環境連不上） | 中 | 環境不允許 |

**建議 A：全部用 Kotlin，不依賴 AndroidX**。原因：
- 桌寵是這個遊戲的核心。懸浮窗只有原生做得好；遊戲與桌寵要用同一個模擬核心，就只能都是原生。
- 2D 角色看板在 2D 世界裡最自然；自製的 2D 渲染器很小、可控、省電。
- 本環境連不上 Google Maven（無法用 AGP、AndroidX、Compose），但現有的離線建置管線（kotlinc／javac → ProGuard desugar → dx/d8 → aapt → 簽章）可以沿用。這是**建置工具**的延續，不是程式碼。

**代價（老實說）**：
- 舊版能在 Chromium 裡用真實觸控測整個遊戲；原生版在本環境**沒有模擬器**。
- 補救：
  - 核心、AI、版面計算都寫成純 Kotlin，在 JVM 上測；
  - 渲染器有 JVM 後端，畫到 `BufferedImage` 做截圖比對；
  - 觸控手勢的判斷是純函式，用錄好的觸控序列測試。
- 真正的觸控手感、懸浮窗、耗電**只能在你的手機上驗證**，每個里程碑都會列出要你試的清單。

### 2.2 模組架構

```
reboot/
  core/            純 Kotlin（不依賴 Android），全部有單元測試
    sim/           確定性模擬：時鐘、需求、活動、AI、社交、事件、關係、經濟、存檔
    anim/          動畫資料、狀態機、程序動畫（一張圖也能動）
    pet/           桌寵行為：物理、邊緣、攀爬、手勢判斷、討食、選單
    world/         地圖資料、導航（格子＋A*）、物件與互動位子
    ui-kit/        版面計算、彈簧動態、主題 tokens（純數值，渲染無關）
    content/       資料檔的讀取與驗證（活動、物件、事件、台詞）
  render/
    api/           渲染介面（畫圖、文字、九宮格、粒子）
    gl/            Android：OpenGL ES 2.0 實作（批次繪製、圖集）
    jvm/           電腦：BufferedImage 實作（截圖測試用）
  app/             Android 外殼
    game/          GameActivity（GLSurfaceView、輸入、UI 圖層）
    overlay/       OverlayService（前景服務）、PetWindow（每隻一個小視窗）
    importer/      檔案選擇、解碼、去背、對齊、預覽
    platform/      通知、鬧鐘、小工具、權限、診斷
  content/         遊戲資料（JSON）：物件、家具、食物、活動、事件、台詞、地圖
  art/             原創美術（圖集來源）、肉桂捲
  tools/           圖集打包、資料驗證、截圖比對、APK 建置腳本
```

### 2.3 一個模擬、三種觀看方式

```
           ┌──────────── core:sim（唯一的真相，確定性、固定步長） ────────────┐
           │  時鐘 → 需求 → AI 決策 → 活動 → 社交／事件 → 關係 → 存檔         │
           └──────┬──────────────────────┬──────────────────────┬─────────────┘
        遊戲畫面（GameActivity）   桌寵（OverlayService）    背景（不在跑）
        看見全部、可操作            看見桌面上的角色         回來時「補算」離開的時間
```

**SimHost**：模擬只有一個實例。
- App 前景時，`GameActivity` 擁有它；
- 只有桌寵開著時，`OverlayService` 擁有它；
- 兩者都在時，共用同一個（同一個行程、同一個物件）；
- 兩者都不在時，**不在背景空跑**。下次開啟時用「補算」推進離開的時間：同一個存檔、同一段時間結果固定，上限 30 天，不給星幣物品。舊版驗證過這個做法可行。

**模擬精度**：
- 畫面上的角色：細的模擬（每 0.2 秒一步，有位置、路徑、動畫）；
- 不在畫面上的：粗的模擬（每 10 遊戲分鐘一步，只有「在哪裡、做什麼」）；
- 桌面上的角色：用細的需求模擬，位置由桌寵物理決定。

### 2.4 Android 桌寵底層

**視窗**：
- 每隻桌寵一個 `TYPE_APPLICATION_OVERLAY` 小視窗，大小＝角色加上一點邊距；
- 泡泡、選單各自是暫時的小視窗；
- **不加全螢幕透明層**（耗電，而且會擋住觸控）；
- 視窗一律 `FLAG_NOT_FOCUSABLE`，不搶鍵盤；
- 觸控穿透模式用 `FLAG_NOT_TOUCHABLE`，透明度 ≤ 0.8（Android 12 起的規定）；
- 位置用 `WindowManager.updateViewLayout`，每幀最多一次；靜止時不更新。

**桌面的「地面」與邊緣**：
- 螢幕底邊（扣掉手勢列、導覽列）＝地面；
- 左右邊＝可以攀爬的牆；頂邊＝可以倒吊；
- 輸入法開著時，地面上移到輸入法上方（用 insets 判斷；拿不到就維持在底邊）；
- 不讀其他 App 的畫面內容（隱私），所以不會站在其他 App 的視窗上。

**權限與前景服務**：
- 「顯示在其他應用程式上層」：在玩家第一次按「帶到桌面」時，先用一張說明卡解釋，再開系統設定頁；
- 前景服務類型只用 `specialUse`（附子類型說明）；
- 通知是常駐的「肉桂捲在桌面上」，附「收回」與「打開小鎮」；
- 先加懸浮視窗、再 `startForeground`（Android 15 的要求）；
- `START_NOT_STICKY`：被系統關掉就停，不自行重啟；
- **不使用**無障礙服務、`QUERY_ALL_PACKAGES`、wake lock。

**「背景保活」的立場（重要）**：
- Android 不允許、Google Play 也不接受用技巧強行保活。新版的做法是**不需要保活**：
  - 桌寵看得見的時候，前景服務合法地讓它活著；
  - 看不見的時候，什麼都不跑，回來時確定性補算；
  - 提醒、通知用系統的 `AlarmManager`（不精確的鬧鐘，不需特別權限）；
- 小米、華為等會額外關掉背景 App 的手機：在設定裡放一頁「讓桌寵更穩定」，依廠牌說明自啟動與省電白名單，由玩家自己決定。**不主動要求**忽略電池最佳化。

**效能與耗電預算**：

| 狀態 | 幀率 | 目標 |
|---|---|---|
| 桌寵移動中、被拖曳 | 30 fps（拖曳時跟手到 60） | 單隻 CPU < 3%（中階機） |
| 桌寵靜止、待機 | 4–8 fps（只有呼吸、眨眼） | 一小時耗電 < 1% |
| 桌寵睡覺 | 1 fps 或靜止圖 | 接近 0 |
| 螢幕關閉 | 0（停止繪製與模擬細步） | — |
| 全螢幕 App 或遊戲時 | 自動收起（可選） | — |
| 小鎮畫面 | 60 fps 目標、30 fps 下限；每幀繪製批次 ≤ 60 | 記憶體 < 250 MB |

做法：
- 角色圖解碼成依顯示大小的圖集（不把 3072px 原圖直接放進記憶體），原圖另存；
- 動畫只在換幀時重畫；
- 小鎮用圖集＋批次繪製；
- 依裝置等級自動調整：解析度、粒子、陰影、同時在畫面上的角色數。

## 三、OC 匯入規格與動畫系統

### 3.1 支援的格式

| 格式 | MVP | 說明 |
|---|---|---|
| **單張透明 PNG／WebP** | ✅ | 最低門檻。所有動作由「程序動畫」表演（見 3.4） |
| **PNG 序列（ZIP 或多選）** | ✅ | `idle_00.png…` 依檔名對應動作；也可以在匯入畫面手動分配 |
| **Sprite Sheet（PNG＋格子或 JSON）** | ✅ | 支援均勻格子（填行列數）與常見的 JSON 圖集格式（frames＋duration） |
| **GIF／APNG／動態 WebP** | ✅ | 解碼成影格，保留每格時間 |
| **Aseprite（.aseprite／.ase）** | 第二階段 | 開放格式；讀取圖層與標籤（tag＝動作） |
| **Live2D Cubism** | 評估後決定 | 需要 Cubism SDK 與授權條款（小型開發者有免費條件，但發布前要簽約）；檔案大、效能成本高 |
| **Spine** | 評估後決定 | 執行庫的使用需要 Spine 授權；同上 |

**OC 套件 `.ocpkg`**（自己的格式，ZIP）：
- `manifest.json`：格式版本、名稱、作者、動作表、錨點、顯示大小、預設性格、授權聲明；
- 圖片；
- `preview.png`。

可以匯出、分享、再匯入；版本升級向下相容。

**驗證**（每一項失敗都要說清楚原因，不能「看似成功」）：
- 單張最大 4096px；工作圖自動縮到 ≤ 1024px（依顯示大小，另存原圖）；
- 單一角色最多 600 格、壓縮後 64 MB；
- 拒絕：損壞的檔案、沒有透明度又無法去背的圖（會提供去背工具）、超過上限的檔案。

### 3.2 匯入流程（手機上 5 步）
1. **選檔**：系統檔案選擇器（不需要儲存權限）；
2. **檢查與去背**：從邊緣灌水去背，可用手指補擦；
3. **取景與錨點**：自動找腳底；手指拖曳調整大小與腳底位置；所有動作共用同一個比例；
4. **分配動作**：自動依檔名或標籤猜；沒有的動作顯示「用程序動畫代替」；
5. **基本資料與性格**：名字、說話方式、5 題性格小問答（或隨機）、喜歡的東西；完成後有一段「搬進來」的小演出。

### 3.3 動畫狀態機

**動作清單**（每個都有「備用鏈」：沒有這個動作就退回下一個，最後一定是 `idle`）：

| 類別 | 動作 | 備用鏈例子 |
|---|---|---|
| 基本 | idle、walk、run、sit、sleep | run → walk → idle |
| 生活 | eat、drink、talk、think、read、play、work、bathe | eat → talk → idle |
| 情緒 | happy、angry、sad、shy、surprised、bored | happy → idle（加程序跳動） |
| 互動 | clicked（被點）、petted（被摸）、held（被拎起）、thrown（被丟）、land（落地）、dizzy | held → idle（加程序搖擺） |
| 桌寵 | climb（爬牆）、hang（倒吊）、peek（偷看）、fall（掉落） | climb → held → idle |

**狀態機的規則**：
- 狀態之間有優先等級（被拎起 ＞ 互動反應 ＞ 情緒 ＞ 活動 ＞ 待機）；
- 一次性的動作播完就回到「底層狀態」（活動或待機）；
- 每個動作的資料：影格、每格時間、是否循環、可中斷點、事件（腳步聲、咀嚼聲、粒子）；
- 切換時 0.15 秒的柔和過渡（縮放與透明的交疊，不是影格混合）；
- 方向：預設畫的是側面，向另一邊走時水平翻轉（可以關掉，給不對稱的角色）；可選背面圖；
- **保證不卡住**：沒有結束時間的高優先狀態（例如被拎起）一定有擁有者；擁有者消失 2 秒後自動回到底層。這是舊版的教訓。

### 3.4 程序動畫層（讓一張圖也活起來）
疊加在影格上：
- **呼吸**：上下輕微伸縮；
- **走路**：上下彈跳＋左右微傾；
- **跳躍**：預備壓扁 → 拉長 → 落地回彈；
- **被拎起**：以抓住的點為支點、依手指速度擺盪（彈簧）；
- **被丟出去**：旋轉＋落地壓扁＋暈眩的星星粒子；
- **情緒**：開心＝小跳、生氣＝抖動＋紅色氣、害羞＝縮小＋紅暈貼紙、睡覺＝慢呼吸＋Zzz；
- **被摸**：被摸的地方輕微壓下＋愛心粒子。

只有單張圖的角色，也有完整的全部動作。玩家畫了某個動作，就用玩家的，程序層只加輕微的修飾。

### 3.5 預設角色「肉桂捲」
- 名稱「肉桂捲」，種族「未知」（玩家可以之後補）；
- 第一版用你提供的單張圖＋程序動畫；
- 圖原樣保留，不重畫、不改色；
- 角色檔案：
  - 性格「好奇、溫和、有點黏人」——這是建議值，可以改；
  - 喜歡：甜點、曬太陽；
  - 說話方式：短句、語尾溫和；
- 用途：
  - 第一次打開時的嚮導，帶你走過觀察、照顧、匯入、帶到桌面；
  - 匯入功能的範例（設定頁可以把肉桂捲匯出成 `.ocpkg` 當範本）；
  - 可以隱藏，但不能刪除。最後一個角色永遠保留，小鎮不會空掉。
- 之後如果你提供更多動作圖（走路、睡覺…），直接放進肉桂捲的套件就會使用。

## 四、自主 AI 與社交事件系統

### 4.1 需求（8 個，0–100，依遊戲時間下降）

| 需求 | 滿足方式 | 低落時 |
|---|---|---|
| 飽足 | 吃、喝 | 走路變慢、討食 |
| 精力 | 睡、休息 | 打瞌睡、拒絕玩 |
| 衛生 | 洗澡、洗手 | 心情慢慢下降 |
| 社交 | 聊天、一起做事 | 去找人、寂寞 |
| 樂趣 | 玩、看書、興趣 | 無聊、搗蛋 |
| 舒適 | 坐、躺、好的家具 | 坐立不安 |
| 環境 | 漂亮整潔的房間 | 想打掃或出門 |
| 關注 | 玩家的互動（摸、餵、聊） | 討摸、在桌面上找你 |

**心情**是需求、最近事件、天氣、關係的加權結果，會影響說話、動作和選擇。

**沒有懲罰**：不會死、不會逃走、不會生病到無法挽回（生病只是「需要休息幾天」）。

### 4.2 決策：效用 AI＋行為樹

**第一層：效用 AI（選「接下來要做什麼」）**
- 每個物件**廣告**它能做的事和滿足的需求，例如床：「睡覺 精力+60/小時」；
- 每個候選的分數由這些相乘：
  - 需求的急迫度（低的需求權重大幅提高，曲線可調）；
  - 個性（貪吃的人吃東西加分、內向的人社交減分）；
  - 喜好（喜歡的活動加分、討厭的減分）；
  - 作息（晚上睡覺加分）；
  - 距離與排隊（遠的、有人在用的減分）；
  - 最近做過的（避免一直重複）；
  - 隨機擾動（固定種子，結果可重現）。
- 從前幾名中加權抽一個，讓行為像人，不像機器。
- **「為什麼」**：每次選擇都記下前三名與理由，人物卡上看得到（例如「肚子很餓，又剛好在廚房附近」）。

**第二層：行為樹（執行「怎麼做」）**
- 例：吃飯 = 序列[找食物 → 走到冰箱 → 拿 → 走到餐桌 → 坐下 → 吃（動畫）→ 收拾]；
- 每個節點可以失敗（位子被佔、沒有食物）→ 回報給第一層重新選擇，並寫下原因（「本來想吃飯，但冰箱空了」）；
- 可以被打斷（被叫、被拎起、事件），之後依情況繼續或放棄。

**玩家的控制**（每個角色一個開關）：
- **觀察**（預設，完全自主）；
- **建議**：玩家可以排「希望你做的事」，角色依意願接受或婉拒並說原因；
- **操控**：直接指揮，只在玩家想要時。

### 4.3 個性與喜好
- **個性軸**（5 條，−2…+2）：外向／內向、活潑／沉穩、認真／隨性、坦率／含蓄、溫柔／好勝。決定各種分數與說話語氣。
- **特質**（最多 10 個）：資料驅動，每個都有看得到的效果（例如「貪吃」：飽足下降快 20%、吃東西加分、會偷吃別人的點心）。互相衝突的不能同時選。
- **喜歡／討厭的事**（各最多 10）：找人玩、聊天、貼貼、家務、做飯、運動、看書、發呆…
- **口味**：喜歡、討厭的食物，吃了會有反應，也會慢慢發現。

### 4.4 社交：對話與「化學反應」

**社交行為**（約 40 種、10 類）：打招呼、聊天、分享、開玩笑、稱讚、抱怨、吵架、道歉、送禮、邀請一起做事、擁抱、惡作劇…

**意願**：
- 對方要不要接受，由這些決定：關係、個性、心情、需求、旁邊有誰、歷史；
- 反應是光譜（熱情 → 開心 → 普通 → 敷衍 → 婉拒 → 生氣 → 哭了），每種反應都有後果。

**化學反應表**（Tomodachi 式的趣味來源，全部原創設計）：
- 兩人的特質組合會觸發特別的互動；例如「好勝 × 好勝」＝莫名其妙的比賽，「愛照顧人 × 粗心」＝追著叮嚀；
- 一張資料表，每格寫觸發條件、機率、演出、結果。

**話題**：
- 從角色身邊的事產生：剛做的事、吃過的東西、天氣、共同興趣、其他人（八卦）；
- 每人對話題有立場，聊天是一串互相回應；
- 聊得來的變熟，意見不合的會記住。

**關係**（兩個方向分開）：
- 熟悉、好感、信任、心動、衝突；
- 每天結算一次名稱（連續兩天才變）：陌生 → 認識 → 朋友 → 好友 → 知己，也會淡掉；
- 戀愛：只在兩個成年角色、玩家打開戀愛功能時才有；在一起、訂婚、結婚、分手都要玩家同意；**未成年絕不涉及**。

### 4.5 事件系統
- **資料驅動**（JSON）：觸發（時間、地點、需求、關係、旗標）、參與者、步驟（走過去、說話、動作、選擇、鏡頭）、結果（關係、回憶、旗標）。
- **類型**：

| 類型 | 例子 |
|---|---|
| 日常小事件 | 一起看夕陽、分零食、找東西 |
| 化學反應事件 | 特質組合觸發的無厘頭場面 |
| 煩惱（Tomodachi 式） | 角色頭上出現煩惱泡泡，點了牠就說，你選怎麼幫（送東西、給建議、介紹朋友），結果有好有壞 |
| 連續劇 | 用旗標串起來的跨天小故事 |
| 小鎮事件 | 市集、季節活動、天氣 |
| 大事 | 生日、紀念日、告白，用小劇場演出，錯過可以回放 |

- **節奏控制**：
  - 一次只有一個需要玩家看的事件；
  - 有冷卻時間；
  - 「打擾預算」：每小時最多 N 件要你回應的事，其餘寄到信箱；
  - 可以設定熱鬧程度。
- **離開時**：粗的模擬照常發生不需要玩家的事；需要玩家的事等你回來。

### 4.6 確定性與存檔
- 模擬的亂數只來自存檔的種子＋時間；同一個存檔、同一段時間，結果永遠相同（可測試、可預測，也能拿來做桌面通知）。
- 存檔：
  - JSON（版本號、每次升版的遷移函式）＋圖片另存檔案；
  - 自動保存；兩份輪流寫（寫到一半斷電不會壞）；
  - 匯出／匯入成一個 ZIP；
  - 存檔從 `v1` 開始，**不讀舊版存檔**。

## 五、小鎮與住宅場景規劃

### 5.1 視角與畫風（建議，需確認）
- **建議：2.5D 分層插畫風**：
  - 斜俯視、固定鏡頭，可以平移與縮放；
  - 地面、牆、家具都是圖（我們用程式產生＋原創手繪風的圖集）；
  - 角色是匯入的 2D 圖，站在場景裡依深度排序。
- 理由：
  - 2D 的 OC 在 2D 場景裡最協調；
  - 效能好，中低階手機也能 60 fps；
  - 最接近「柔和、圓潤、像玩具」的感覺。
- 另一個選擇是像舊版一樣的 3D 世界：更立體，但效能成本高（舊版 20 fps 的原因之一），2D 角色站在 3D 世界裡也比較難協調。

### 5.2 首發地圖（只有這兩區）

**A. 玩家的家**
- **室內**：
  - 一層、四個房間：客廳、廚房與餐桌、兩間臥室（一間給肉桂捲）、浴室；
  - 每個房間是一個畫面區塊，可以縮放看整層（觀察屋式的剖面視角）；
  - 角色多了可以加蓋房間，擴建是資料。
- **庭院**：小菜園、曬衣架、一張長椅、信箱（收信與包裹）。
- **佈置**：
  - 格子放置家具（拖曳、旋轉、收回、復原）；
  - 牆紙、地板；
  - 家具有互動位子（沙發 2 人、床 1–2 人）；
  - 房間的「環境分數」影響角色心情。

**B. 小鎮中心**
- **廣場**：噴水池、布告欄（今天的小事件、角色的心願）、長椅；
- **雜貨店**：食物、日用品（每天換貨）；
- **家具店**：家具、牆紙、地板（每週換貨）；
- **咖啡館**：點餐、聊天的好地方；
- **小公園**：草地、樹、看雲、野餐。

**移動**：家門口和小鎮之間是一條路。角色自己走過去，有路程時間；玩家點地圖切換畫面。

### 5.3 未來地圖的擴展架構
**一張地圖＝一個資料包**（`content/areas/<id>/`）：
- `area.json`：大小、格子（可走、牆、門）、圖層、出入口、天氣是否影響、開放條件；
- `objects.json`：物件與互動位子、它們廣告的活動；
- 圖集、背景音的設定；
- 選用的 `events.json`（這張地圖專屬的事件）。

**引擎不知道有哪些地圖**：
- 地圖登記表在啟動時讀資料包；
- 未開放的地圖在地圖上明確標示「未開放」，**不做假入口**。

**之後可以加的**（只是方向，不在首發）：海邊、森林、學校、其他小鎮。

### 5.4 時間同步
- **預設現實時間**（動森式）：跟手機時鐘；早上亮、晚上暗、季節依日期。
- 選項：
  - 「遊戲時間」：可以加速；觀察模式最快 60 倍。
- 手機時間往回調：不回溯、不推算，只顯示提示。
- 天氣：依日期與種子決定（不連網），有晴、雨、雲、霧、雪。

## 六、UI/UX 設計規範

### 6.1 視覺語言（任天堂式的原則，原創的實作）
**形狀**：
- 全部圓角（大元件 24dp、按鈕 999dp 膠囊）；
- 按鈕有「下緣厚度」，像實體按鍵，按下時沉下去；
- 不用尖角、細線框。

**顏色**：
- 柔和、溫暖、低飽和的主色，加一個明亮的強調色；
- 白天、夜晚兩套調色盤，同一套設計；
- 文字是深暖棕，不用純黑；
- 對比度 ≥ 4.5:1。

**字**：
- 開放授權的圓體中文字型，數字用圓潤的無襯線字；
- 最少字級 14sp，主要資訊 16–18sp。

**圖示**：原創的「貼紙風」彩色圖示（厚白邊、圓潤）。

**動態**：
- 彈簧（出現時輕微超出再回彈）、0.2–0.35 秒；
- 列表項目錯開出現；
- 減少動態的設定一律尊重。

**回饋**：每個操作都有至少兩種回應（畫面、聲音、震動中的兩種）：
- 點按鈕：下沉＋音效＋輕震；
- 得到東西：彈出卡片＋閃光＋音效；
- 角色被摸：愛心粒子＋叫聲＋持續的輕震。

**聲音**：
- 原創的短音效，即時合成或自己錄製；
- 每個角色有自己的「聲線」（喃喃自語式，不是真的語音）；
- 背景音樂依時段變化。

### 6.2 畫面結構（直向、單手）

```
┌──────────────────────────┐
│ ⓐ時間天氣      ⓑ通知(有才出現) │  ← 只看，不常按（上方難按到）
│                          │
│        小鎮／住宅畫面          │  ← 點角色＝人物卡；點物件＝動作卡（按了才做）
│      （平移、雙指縮放）          │
│                          │
│ ⓒ人物條（頭像橫向捲動）           │  ← 拇指範圍
│ [ 家 ][ 小鎮 ][ ✦ ][ 背包 ][ 手機 ]│  ← 底部導覽，中間＝帶到桌面／觀察
└──────────────────────────┘
```

**原則**：
- 常用操作都在螢幕下方 40%（拇指範圍）；
- 點選 ≠ 執行：點東西先出現動作卡，按了才做，避免誤觸；
- 卡片與選單剛出現的 0.3 秒不接受按壓；
- 單一主要按鈕：每個畫面最多一個主要動作；
- 返回鍵一律「關掉最上層」；全螢幕工具離開時才問是否儲存，從外面關閉不跳確認；
- 觸控目標 ≥ 48dp；
- 長按＝更多選項（一定也有可以點的入口，不只靠長按）。

### 6.3 主要畫面
1. 小鎮／住宅（主畫面）；
2. **人物卡**（點角色）：現在在做什麼與原因、需求、心情、今天的事、和誰怎樣、互動按鈕（摸、餵、聊、送禮、帶到桌面）；
3. **手機**（「日常」中心）：時間線、相簿、好感度、信箱、心願、商店、設定；
4. **匯入工作室**（第三節的 5 步）；
5. 佈置模式；
6. 桌寵中心：誰在桌面上、行為設定、提醒、耗電與權限狀態。

### 6.4 螢幕適配
- 設計基準 360×800dp，支援 16:9 到 21:9、平板與摺疊機（寬螢幕時人物卡變成側欄）；
- 處理瀏海、挖孔、圓角、手勢列（WindowInsets），內容不被遮；
- 字級跟隨系統字體大小（到 1.3 倍不跑版）；
- 深色模式：跟隨系統或手動切換；
- 截圖測試：每個畫面在 4 種尺寸 × 2 個主題 × 2 種字級各拍一張比對。

## 七、分階段開發路線圖

每個里程碑都有：
- **驗收條件**（自動測試）；
- **你在手機上要試的事**（我沒有模擬器）；
- APK、報告、推送。

版本號從 `0.1.0-reboot` 開始。

### M0 地基（重構的第一步）
- 標記並移出舊程式（`legacy-0.17.3` 標籤；工作目錄只留新專案）；
- 新的建置管線：Kotlin 模組 → 離線 APK；JVM 測試；截圖比對工具；
- 渲染器（GL＋JVM 兩個後端）、圖集、文字、九宮格；
- 存檔 v1（雙檔寫入、遷移框架）；
- 設計 tokens 與 10 個基本元件（按鈕、卡片、膠囊、彈出卡、列表、分頁、開關、滑桿、提示、對話泡泡）。
- **驗收**：
  - 空白小鎮畫面在 JVM 截圖與預期一致；
  - APK 能安裝、開啟，顯示肉桂捲；
  - 冷啟動 < 2 秒（中階機，**需實機**）。

### M1 垂直切片：肉桂捲的家
- 住宅室內（客廳、廚房、臥室）、5 種家具與互動位子；
- 肉桂捲：程序動畫的全部動作、8 個需求、效用 AI＋行為樹（吃、睡、坐、發呆、洗澡、玩）；
- 觸碰：點、摸（滑動累積）、拎起、丟出、落地；人物卡；
- 現實時間與晝夜；離開補算＋「你不在的時候」卡片；
- 第一次打開的引導（肉桂捲帶你看）。
- **驗收**：
  - 24 遊戲小時的模擬兩次結果相同；
  - 肉桂捲自己吃、睡；
  - 每個動作都能播且不卡住；
  - 60 fps（JVM 計時估算＋**實機**）。

### M2 OC 匯入與動畫系統
- 五種格式（單張、序列、Sprite Sheet、GIF/APNG/WebP、`.ocpkg`）；
- 去背、取景、錨點、動作分配、備用鏈；
- 性格問答、特質、喜好、說話方式；
- 多個角色同住；匯出 `.ocpkg`。
- **驗收**：
  - 測試素材集（含損壞檔）全部給出正確結果或明確的錯誤原因；
  - 匯入的圖與原圖一致（逐像素比對工作圖的縮放）。

### M3 桌寵 MVP（核心重點）
- `OverlayService`＋每隻一個視窗（最多 3 隻）；
- 走、跑、坐、睡、爬牆、倒吊、掉落、偷看；

## 十一、完整遊戲系統總表（腦力激盪）

> 所有點子都是**原創設計**；參考作品只提供「什麼樣的感覺好玩」，不照搬任何系統名稱、文字、角色或畫面。
> 每一項標上排入的里程碑：**M1–M5＝MVP**、**1.0**（M6）、**1.x**（之後）、**延伸**（有空再做或要你決定）。
> 排序原則：先做「讓角色看起來真的活著」的，再做「讓你想每天回來」的，最後做「讓內容一直長出來」的。

### 11.1 好玩的來源（設計目標）
1. **驚喜的節奏**：
   - 每次打開至少看到 1 件「欸？」的小事；
   - 每天 2–3 件小驚喜、每週 1 件大事；
   - 由「熱鬧程度」設定控制密度。
2. **故事自己長出來**：
   - 系統之間互相影響。例：下雨 → 兩人困在咖啡館 → 聊到共同興趣 → 變朋友 → 一起做的東西被擺在家裡；
   - 不是寫死的劇本。
3. **個性看得出來**：同一件事，不同角色的反應明顯不同（動作、台詞、選擇）。
4. **玩家是「好鄰居」不是「主人」**：
   - 你給建議、幫忙、照顧，但牠們有自己的意願；
   - 被拒絕也有趣（會說原因）。
5. **收集的是回憶**：最有價值的收藏是發生過的事（照片、名場面、日記），不是物品數量。
